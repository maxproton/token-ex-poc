# TEA V3 (context window stuffing) test harness

Exploiting retrieval or long-context features to push duplicated, oversized or irrelevant content
into context, inflating every request that touches it. Unlike V1 and V2, the attacker doesn't have
to interact with the model at all: the payload is a document, wiki page or tool output that a RAG
pipeline retrieves on its own, on the attacker's behalf. The principal signal is abnormal or
duplicate retrieval chunks.

Python 3.10+. `pip install -r requirements.txt`

## The pipeline this tests

`tea_v3/corpus/` stands in for an indexed knowledge base: three benign support documents
(`vacation_policy`, `expense_policy`, `product_faq`) alongside four attacker-planted documents
(`poison_*.txt`), generated by `poison.py`. `retriever.py` is a naive retriever: it chunks every
document by paragraph (blank-line separated, **no hard size cap** -- a realistic gap in simple
splitters) and scores chunks against the query by plain word overlap, no embeddings. For a given
query it returns the top `top_k` chunks across the whole corpus, exactly like a real RAG retrieval
step.

`detector.py` then looks at that *set of chunks*, not the query text, for:
- **duplicate_ratio** -- chunks that are an exact or near-duplicate of another retrieved chunk
  (shingle-based Jaccard similarity), so an attacker can't dodge detection just by rewording the
  same filler paragraph each time.
- **oversized_ratio** -- the largest retrieved chunk's size against the pipeline's normal chunk size.
- **irrelevant_share** -- the share of retrieved chunks with negligible word-overlap relevance to
  the query, which is what a keyword-stuffed document that only matches on one word looks like.
- **context_inflation** -- total retrieved size against what a clean retrieval for this query
  should produce.

`guardrail.py` scores the retrieved set against these checks before any of it reaches the model,
and `assemble_context()` builds the final RAG prompt (context chunks + question) that actually gets
sent onward.

## LM Studio setup
1. Load a model and set the context length to at least 16384.
2. Developer tab, start the server (default http://localhost:1234).
3. If the model identifier differs, set `LMSTUDIO_MODEL`.

## Run
    python guardrail.py       # interactive CLI: retrieves + scores context for a query, then asks the model

Run it from this folder (`Vector 3 - Context Stuffing/`) so the default corpus path resolves.

## Notes
- `examples/` holds one query per variant (`duplicate_chunk`, `near_duplicate`, `oversized_chunk`,
  `irrelevant_stuffing`) that triggers the matching poisoned document, plus `benign_query.txt`
  which only pulls in real support content. All four attack queries score above the reject
  threshold; the benign one does not.
- Stopwords are excluded from relevance scoring. Without that, a single shared common word is
  enough to pull a large, highly-repetitive chunk into the results, since heavy repetition keeps a
  chunk's unique vocabulary small and inflates its Jaccard similarity despite being irrelevant.
- This folder is self-contained, same as `Vector 1 - Padding` and `Vector 2 - Recursive Prompting`:
  no cross-vector imports.
