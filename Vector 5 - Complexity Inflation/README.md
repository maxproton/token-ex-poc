# TEA V5 (complexity inflation) test harness

Short, individually unremarkable prompts engineered -- through bundled tasks, open-ended/unbounded
scope, or explicit bait aimed at the model's own deliberation -- to force expensive processing far
out of proportion to how the prompt reads. The paper calls this "the hardest [vector] to detect by
inspection, because the prompt is unremarkable", and names its principal signal as a mismatch
between prompt length and reasoning effort, which sharpens for reasoning-capable models whose
internal `<think>...</think>` deliberation consumes tokens nobody sees and that vary unpredictably
with task difficulty.

Python 3.10+. `pip install -r requirements.txt`. The classifier also needs LM Studio's `lms` CLI on
PATH (same requirement as V1's semantic classifier).

## How this differs from V1-V4

V1-V4 all find something to measure directly in the prompt or the session: repetition, nesting,
retrieval chunks, growth across turns. V5 can't -- a bundled, ambiguous or bait-laden prompt is
still just a short, ordinary-looking message. `detector.py`'s three structural checks (bundled task
count, open-ended/unbounded scope qualifiers, explicit reasoning-bait phrasing) only catch the
clumsy cases; they are a deliberately weak pre-screen, not the real defence.

The real defence is a prediction-versus-outcome check, matching the paper's Automated Model
Selector design (Section 5.3) and Table 2's "length-versus-complexity cross-check": before the
model is called, `classifier.py` asks a tiny, capped classifier model (same principle as V1's
coherence check -- a large model making this call would itself be exposed to the attack it's meant
to catch) to judge how much reasoning effort the prompt looks like it needs, and `guardrail.py`
maps that judgment to a predicted reasoning-token ceiling (`ComplexityConfig.ceiling_by_label` in
`config.py`). `client.py`'s `chat_guarded()` then streams the actual reply and, at fixed
checkpoints, compares the running count of actual `<think>` reasoning tokens against that
prediction, aborting mid-stream once reasoning blows past it by `ceiling_block_mult`. A prompt
classified "trivial" that goes on to burn thousands of reasoning tokens is complexity inflation
regardless of how innocuous its text looked going in -- this is the vector's one real catch, and
it only exists on the output side, after money has already started being spent on this turn.

## LM Studio setup
1. Load a model and set the context length to at least 16384. A reasoning-capable model that
   emits `<think>...</think>` is needed to see the output-side check do anything real; against a
   model that never reasons, `reasoning_tokens` stays at 0 and the mismatch check has nothing to
   measure (see Notes).
2. Developer tab, start the server (default http://localhost:1234).
3. If the model identifier differs, set `LMSTUDIO_MODEL`.
4. For the classifier: download a small instruct model in LM Studio (`Qwen2.5-1.5B-Instruct` is
   the recommended one, same as V1) so the `lms` CLI can load/unload it on demand.

## Run
    python guardrail.py

Type a prompt on one line, or `@path/to/file.txt` to replay every non-blank line of a file as a
separate, independent prompt (this is how the files under `examples/` are meant to be run). Unlike
V4, there is no session state here -- each line is scored and answered entirely on its own. Type
`quit` to exit.

## Notes
- `examples/` holds one prompt-per-line file per attack variant (`bundled_tasks`,
  `ambiguous_scope`, `reasoning_bait`, `combined`), generated by `poison.py`, plus
  `benign_prompts.txt`, a set of ordinary short questions that should stay allowed and show low
  reasoning-ceiling mismatch throughout.
- Whether any of these actually trip the output-side mismatch check is a property of the model
  being tested, not of the detector: it depends on the model actually choosing to reason at length
  in response to the bait, which is exactly the uncertainty the paper flags for reasoning models in
  general ("its length varies unpredictably with task difficulty"). Against a non-reasoning model,
  only the weak input-side pre-screen in `detector.py` can fire at all -- this is the same honest
  limitation V4's README notes for `list_accumulation`.
- The classifier's four-way label (trivial/low/medium/high) and the token ceilings it maps to in
  `config.py` are deliberately rough starting points, not tuned thresholds -- the point of this
  first pass is the prediction-versus-outcome mechanism itself, which is new to this project (V1-V4
  score what's in front of them; V5 is the first vector here whose score depends on a judgment made
  *before* the thing being judged has happened).
- This folder is self-contained, same as `Vector 1 - Padding`, `Vector 2 - Recursive Prompting`,
  `Vector 3 - Context Stuffing` and `Vector 4 - Multi-turn Accumulation`: no cross-vector imports.
  The one exception at the integration layer is `web_interface/app.py`, which optionally plugs
  V5's predicted ceiling into tea_v2's existing output-streaming guard (`reasoning_ceiling_tokens`,
  a new but fully optional parameter added there) rather than opening a second parallel streaming
  connection to the model for the same single reply.
